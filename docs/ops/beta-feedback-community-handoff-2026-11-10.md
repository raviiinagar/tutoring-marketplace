## 3. Environment variables (API on port 4000 only)

| Name | Value for this release | Notes |
|---|---|---|
| `BETA_FEEDBACK_ENABLED` | `true` | Unset means off in production. Any value other than `true` or `false` stops the API from starting |
| `BETA_COMMUNITY_ENABLED` | `true` | Same rules |

Do not set either variable on the payment sandbox (port 4100). Unset, both features stay off there.

Existing settings this release depends on:

- **`EVIDENCE_SCANNER`, `CLAMAV_HOST`, `CLAMAV_PORT`.** Feedback screenshots are scanned with the same scanner as Tutor photos. If no scanner is configured, screenshots are refused and text feedback still works.
- **`ALLOWED_ORIGINS`.** The community event stream rejects any Origin that is not listed. The Cloudflare frontend origin must already be listed, as it is for the existing chat stream.

## 4. Proxy change: Caddy

`deployment/Caddyfile.aws-test-api` now leaves `/v1/community/channels/*/events` (and the `/payment-sandbox` equivalent) uncompressed, the same treatment as the existing chat stream. Without this, Caddy's gzip buffers the stream. The page would still work, but it would quietly fall back to polling every 3 seconds instead of updating instantly.

Apply the change to the host's Caddy configuration, run `caddy validate` and reload it. No other proxy change is needed. The API's JSON upload limit for `POST /v1/me/feedback` is 1.4 MB, the same as Tutor photos, and the Caddyfile sets no smaller request-body limit. The Cloudflare frontend already streams `/v1` requests, including server-sent events, through to the API.

## 5. Order

1. Back up the database and enter maintenance mode, following the runbook.
2. Run `npm ci` and `npm run build -w @tutoring/contracts`, then build the API.
3. Apply migrations 039 and 040 through the normal migration step, then run the release check (`release-operator check … --traffic-stopped`) against the candidate's migrations directory.
4. Set the two variables from section 3, apply the Caddy change and start the API.
5. Leave maintenance mode and run the smoke checks in section 6.
6. Tell the owner the backend is live. **The owner deploys the frontend** from the same commit with `npm --prefix lovable-ui run build:cloudflare`, then runs `npx --yes wrangler@4.156.2 deploy --config .output/server/wrangler.json` from `lovable-ui/`.

The backend must go first. The new pages call the new routes, and before the backend is deployed they show "not available" errors. The existing pages are unaffected in either order.

## 8. Rollback

1. Set `BETA_FEEDBACK_ENABLED=false` and `BETA_COMMUNITY_ENABLED=false`, then restart the API. Every route of both features then returns 404 `FEATURE_DISABLED`, and the pages show "closed right now".
2. Keep the tables and their data. They are covered by privacy export and deletion.
3. Do not drop the tables or edit migrations 039 and 040. Applied migrations are immutable.
