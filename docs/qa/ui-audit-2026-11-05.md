## Coverage gaps and policy caveats

- Dedicated real browser scenarios for the current Super Admin/delegated Admin workflow, free direct ads, saved Tutors, Tutor Pro, higher reputation levels and new account-card editing are not represented in the old tests/browser suite. Newer focused scripts elsewhere may cover some of them; they must be counted separately.
- The current page set has no universal Learner avatar, phone/SMS verification, postal-address editing, in-platform video calling or tuition-payment processing. Existing meeting invitations link externally; Access Pass payment is separate from tuition.
- Many old browser selectors assume the former Dashboard, Tutor onboarding and search wording. Their failures need classification rather than being treated automatically as product failures.
- `tests/browser/tutors.spec.ts` still assumes mandatory identity/qualification and staff ad approval. That conflicts with ADR0014, so it is not a valid acceptance oracle for current free-ad publication.
- Authentication, safety and privileged-route coverage requires both browser and backend evidence. Static route enumeration and component tests alone cannot certify access controls.

## Existing browser-suite harness

`playwright.config.ts` defines one worker and a generated loopback-only `scripts/browser-stack.mjs` web server, using UI3100/API4100 and its own PostgreSQL/browser_test fixtures. The browser launcher is Chrome. The default run has19 tests; the built-mobile performance scenario deliberately skips unless `PLAYWRIGHT_BUILT_UI=true`.

The worktree originally lacked root node_modules. A junction to the existing `D:/WORK/P1/node_modules` was added only after confirming the path did not exist; no installed packages or lockfiles were changed. This unblocks the harness’s hard-coded local tsx/TypeScript paths. Actual browser results and classified failures are recorded in the browser audit after completion.
